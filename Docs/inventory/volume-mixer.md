## Volume composition

The five volume inputs are NOT peers — they compose at two different levels, one multiplicative in the player's
own math, one downstream in the mixer's signal chain:

- Per-player linear multiply (`AudioPlayer.Volume.cs: UpdateVolume`): `vol = _clipVolume.Current * _trackVolume.Current * _audioTypeVolume.Current`, where:
  - `_clipVolume` is seeded once per play from `_clip.Volume * _pref.Entity.GetMasterVolume()` (`AudioPlayer.Playback.cs:274`, entity's `GetMasterVolume()` applies `RandomFlag.Volume` randomization) — this is the clip-level and entity ("MasterVolume" field on `AudioEntity`) volume, **baked together into one Fader** at playback start. They are indistinguishable once playing; a test cannot isolate clip.Volume from entity.MasterVolume via `_clipVolume` alone.
  - `_trackVolume` is the per-`SoundID` volume set by `BroAudio.SetVolume(SoundID, vol, fadeTime)` → `SoundManager.SetVolume(SoundID,...)` → `player.SetVolume(...)` (only players whose `ID.Equals(id)` are affected — active instances only, no persisted per-ID pref for future plays of the same ID).
  - `_audioTypeVolume` is the per-`BroAudioType` volume. `BroAudio.SetVolume(BroAudioType, vol, fadeTime)` both (a) persists into `_audioTypePref[type].Volume` via `SetPlaybackPrefByType` — consumed by every *future* play of that type in `PlayControl` (applied unconditionally, subject only to a `!_audioTypeVolume.IsFading` guard) — and (b) immediately pushes to every *currently active* player of a matching type via `player.SetAudioTypeVolume`.
  - This linear product is converted `.ToDecibel()` and written to the mixer's per-track (or per-send, see Mixer routing) parameter; if no mixer group is attached (`TryGetMixerAndTrack` fails — see Mixer track acquisition edge case) it falls back to `AudioSource.volume = vol.ClampNormalize()` **linear, uncoverted, and bypassing the mixer entirely** (so master volume, below, has no effect on that voice while unrouted).
- Master (`BroAudioType.All`) volume (`SoundManager.SetMasterVolume`) is a *separate* multiplication stage: it writes directly to the mixer's `MasterTrackName` exposed parameter in dB, which every track routes through downstream in the mixer's signal graph. It never touches player Faders, so `IAudioPlayer.GetVolume()` and `_mixerDecibelVolume` never reflect it — only the final analog/digital signal (or `AudioListener.volume`, not modeled here) does.
- `BroAudio.SetVolume(vol, fadeTime)` (no id/type) === `SetVolume(BroAudioType.All, vol, fadeTime)` === master volume path, confirmed by `BroAudio.cs:159-160`.

## Pitch

| Behavior | Observable | Edge cases | Timing class | Regression risk |
|---|---|---|---|---|
| `SetPitch` drives `AudioSource.pitch` directly, clamped to `[-3, 3]` (the only pitch-shifting mechanism since `PitchShiftingSetting` was removed) | `player.AudioSource.pitch` (via the `IAudioSourceProxy`, or `AudioPlayer`'s own `AudioSource` field through reflection) immediately after `SetPitch(id, pitch, 0f)` | Values outside `[MinAudioSourcePitch, MaxAudioSourcePitch]` clamp silently, no log; a fade (`fadeTime>0`) only starts if the player `HasStartedPlaying \|\| AudioSource.isPlaying` — otherwise it's deferred (`_pendingPitchFadeTime`) and consumed later in `SetInitialPitch` | frame (coroutine `PitchControl`, linear `Ease.Linear` lerp hard-coded, ignoring `SoundManager.FadeInEase/FadeOutEase`) / immediate when fadeTime==0 | High — pitch changes are audible and directly gameplay-relevant (e.g. speed-scaled SFX); the linear-only ease here is a real, distinct contract from the volume path's ease-selectable fades |
| `SetPitch` called *before* the player has started playing (fadeTime>0) defers the fade until `SetInitialPitch` runs at play start, fading from the entity's base pitch to the pending target instead of snapping | `player.AudioSource.pitch` sampled at exactly the first playing frame should equal `GetBasePitch(entity, pref)` (not yet the target), then move toward target over subsequent frames | An explicit `SetPitch` before play overrides `entity`'s own pitch-randomization (`GetRandomValue(..., RandomFlag.Pitch)`) — the explicit value wins outright, verbatim, no randomization applied on top | frame | Medium — an easy regression is "always snap immediately," losing the deferred-fade path entirely for never-yet-played players |
| `SetPitch` recalculates the scheduled end time on every pitch change, including mid-fade | `RecalculateScheduledEndTime()` called both on immediate `SetPitch` and every frame of `PitchControl` — a scheduled/looping player's remaining duration should visibly shrink when pitch is raised above 1 | Only meaningful for players with a real `ScheduledEndTime` (looping or scheduled playback) — a plain one-shot has nothing to observe here | frame / immediate | Medium — pitch/scheduling interaction is exactly the kind of cross-cutting bug that regresses silently |
| Master (`BroAudioType.All`) and per-type pitch route through the same `_audioTypePref[type].Pitch` persistence + live-player push pattern as volume | `SoundManager.Instance.TryGetAudioTypePref(type, out pref)` → `pref.Pitch`; live players via `player`'s pitch after `BroAudio.SetPitch(BroAudioType, pitch)` | The two-arg legacy overload `SetPitch(float pitch, BroAudioType audioType)` is `[Obsolete]` but still wired identically to the non-obsolete `SetPitch(BroAudioType, float)` — behaviorally identical, just a deprecated call shape | frame/immediate, same as volume | Low — mechanically identical to the volume per-type path already covered above; only worth a smoke test to confirm the obsolete overload still forwards correctly |

## Mixer track acquisition, routing and dominator path

| Behavior | Observable | Edge cases | Timing class | Regression risk |
|---|---|---|---|---|
| Every non-WebGL player acquires a pooled `AudioMixerGroup` at play start (`SetupAudioTrack` → `Mixer.GetTrack(TrackType)`), Generic by default | `player.AudioSource.outputAudioMixerGroup != null` and its name matches one of the Generic track group names after play start | `IsDominator` (via `AsDominator()` decorator) switches `TrackType` to `AudioTrackType.Dominator` before acquiring, drawing from the separate, much smaller dominator pool | frame (after `Play()` queue drains) | High — routing is the backbone of every other mixer behavior; if a player silently gets no group, volume/effects both degrade to the unrouted fallback described above |
| Returning a player recycles its track back to the correct pool (Generic vs. Dominator) via `IAudioMixerPool.ReturnTrack` | After `Stop`/full lifecycle completion, the pool's available-count observably increases (e.g. play `poolSize+1` concurrent sounds sequentially and confirm the Nth+1 gets a *reused* group, not a `null`/warning) | Returning a track scrubs the parameter to `MinDecibelVolume` first (`SilenceTrackBeforeReturn`) so the next borrower doesn't inherit this player's last volume for one frame — but it inherits the send-effect scrub too if `IsUsingTrackEffect` | frame | Medium — pool return/reuse correctness is easy to break silently (e.g. forgetting to silence before recycle causes an audible "volume blip" for the next borrower) |
| A track with an active effect (lowpass/highpass/custom) routes volume writes to a per-track **send** parameter (`trackName + EffectParaNameSuffix`) instead of the track's own volume parameter, switching live via `mixer.ChangeChannel` | `VolumeParaName` (private, but observable indirectly: `mixer.GetFloat(trackName)` should freeze/scrub to `MinDecibelVolume` while `mixer.GetFloat(trackName+"Send")` (`GetSendParaName()`'s literal suffix — read `BroName.EffectParaNameSuffix` for the exact string) carries the live value) once `SetTrackEffect` toggles a non-`None` effect on | Toggling the effect off again switches back (`ChangeChannel` the other direction) preserving the current dB value across the swap — verify no volume jump at the switch instant | frame (switch is immediate on the `SetTrackEffect` call; write-through happens next `UpdateVolume`) | High — the volume/send parameter swap is a two-parameter dance; an off-by-one in which name is written to produces a silent (literally) player |
| Dominator effect flips the whole main mix between two exposed tracks (`MainTrackName` ↔ `MainDominatedTrackName`) rather than per-player, and reverts automatically once nothing dominant remains | `mixer.GetFloat(BroName.MainTrackName)` drops to `MinDecibelVolume` and `MainDominatedTrackName` rises to `FullDecibelVolume` while a dominator effect (`SoundManager.Instance.SetEffect(effect)` where `effect.IsDominator`) is tweaking or holding; reverts once `EffectAutomationHelper`'s waitable list drains | `DominatorPlayer.QuietOthers/LowPassOthers/HighPassOthers` apply the *complementary* effect to everything *except* the dominator itself (`SetAllEffectExceptDominator`), explicitly clamped/validated (`othersVol` must be `>0 && <=1`, invalid frequency rejected via `AudioExtension.IsValidFrequency`) | frame (coroutine `TweakTrackParameter`) | High — the dominator ducking mechanism is a signature BroAudio feature; the auto-revert-on-drain behavior is exactly the kind of thing a refactor of `EffectAutomationHelper`'s waitable bookkeeping could silently break |
| `IAutoResetWaitable` (`SetEffect` return value) auto-resets the effect back to default once its wait condition (`ForSeconds`/`Until`/`While`) is satisfied | Mixer param for the effect returns to `GetEffectDefaultValue(effectType)` (`FullDecibelVolume` for Volume, `MaxFrequency` for LowPass, `MinFrequency` for HighPass) some time after the waitable's condition becomes true, without any further explicit call | Calling `.While(predicate)`/`.Until(condition)`/`.ForSeconds(n)` *after* the effect has already started tweaking (not on the very next call) logs a warning and is a no-op (`DecorateTweakingWaitable`'s `_latestEffect == EffectType.None` / "isn't the base type" branches) | frame (coroutine `TweakTrackParameter`, condition polled via `WaitUntil`/`WaitWhile`/`WaitForSeconds`) | High — the whole point of the waitable API is "fire and forget, it resets itself"; a broken auto-reset leaves audio permanently ducked/filtered, a very noticeable regression |
| `EffectType.Volume` is rejected outside Dominator context | `SetEffect(Effect.something-with-EffectType.Volume-and-not-dominator)` logs `Utility.LogTitle + "...is only supported on Dominator"` and returns `string.Empty` for the parameter name — effectively a no-op with a logged error | n/a | immediate | Medium — an easy guard to accidentally remove, silently allowing (and presumably crashing or misbehaving on) non-dominator volume effects |
| `EffectAutomationHelper` intensifies rather than restarts: a *more intense* new effect target while already tweaking restarts the coroutine at the new target; a *less intense* one queues and waits | Compare mixer param trajectory when two `SetEffect` calls of increasing vs. decreasing target arrive in quick succession — `Effect.CompareTo`/`IsMoreIntenseThan` (LowPass compares inverted — lower frequency is "more intense") | LowPass's `CompareTo` deliberately flips sign (`Value.CompareTo(other.Value) * -1`) vs. HighPass/Volume — a natural place to introduce a sign-flip bug | frame | Medium — this queuing/intensity logic is the least obvious code path in the whole effects system and the easiest to get subtly wrong in a refactor |
| Mixer pool track-count exhaustion for *any* track type logs a warning and yields `null`, degrading gracefully rather than throwing | `LogAssert.Expect` for the `"You have reached the limit..."` / `"...used up all the [Dominator] tracks..."` warning text, and the player still plays (unrouted) rather than crashing | Dominator vs. Generic pool have separate capacities and separate warning strings | immediate (on `CreateObject` call, itself inside `Extract()`) | Low — already covered by the "sound played after pool exhausted" volume row above; listed here for completeness of the mixer-pool contract |

## EditMode unit-test candidates

These are pure(ish) functions — no MonoBehaviour, no SoundManager, no coroutines — and deserve fast, deterministic
EditMode coverage rather than PlayMode round-trips:

- `Ami.Extension.AudioExtension.ToDecibel(this float vol, bool allowBoost = true)` — linear→dB, including the `ClampNormalize` pre-clamp and the `allowBoost` branch (boundary at `vol == 0`, `vol == 1`, `vol == 10`, `vol > 10`).
- `Ami.Extension.AudioExtension.ToNormalizeVolume(this float dB, bool allowBoost = true)` — dB→linear, including the early-return-at-max-dB branch and `ClampDecibel`. Round-trip property test: `x.ToDecibel().ToNormalizeVolume() ≈ x` for `x` in `[MinVolume, MaxVolume]`.
- `Ami.Extension.AudioExtension.ClampNormalize(this float vol, bool allowBoost = false)` and `ClampDecibel(this float dB, bool allowBoost = false)` — simple clamp helpers, but note the **default** `allowBoost` is `false` here vs. `true` on `ToDecibel`/`ToNormalizeVolume` — worth a test that pins each default independently since a "harmonize the defaults" refactor would be a behavior change.
- `Ami.BroAudio.Utility.SliderToVolume` / `VolumeToSlider` (`Utility.Volume.cs`) — all three `SliderType` branches (`Logarithmic`, `BroVolume`/`BroVolumeNoField`, default/linear), each with `allowBoost` true/false.
- `Ami.BroAudio.Utility.BroVolumeToSlider` / `SliderToBroVolume` — the piecewise `BroVolumeSplitPoints` mapping; test every segment boundary (`-80, -60, -36, -24, -12, -6, 0, 6, 20` dB) plus `sliderValue == 1f` and `sliderValue == 0f` edges. Round-trip property: `SliderToBroVolume(BroVolumeToSlider(v)) ≈ v`.
- `Ami.BroAudio.Utility.GetBroVolumeStep(bool allowBoost)` and the private-but-reachable-via-the-above `GetFullVolumeSplitPointIndex` — pin the step count for boost vs. non-boost (`BroVolumeSplitPoints.Length` vs. the index of `FullDecibelVolume`).
- `Ami.BroAudio.Effect.CompareTo` / `EffectExtension.IsMoreIntenseThan` — pure struct comparison; especially the LowPass sign inversion vs. Volume/HighPass. Also `Effect.IsDefault()` for each `EffectType`.
- `Ami.BroAudio.Effect`'s `Value` setter — confirms `EffectType.Volume` values are stored pre-converted to dB (`value.ToDecibel()`) at construction time, while LowPass/HighPass validate via `AudioExtension.IsValidFrequency` and silently drop out-of-range writes (no exception, no dB conversion).
- `Ami.Extension.AudioExtension.IsValidFrequency(float freq)` — boundary at `MinFrequency` (10Hz) and `MaxFrequency` (22000Hz), logs an error and returns false outside range.
- `Ami.BroAudio.Runtime.AudioTypePlaybackPreference`'s static delegates `OnSetVolume`/`OnSetpitch`/`OnSetEffect` (esp. `SetEffect`'s `Add`/`Remove`/`Override` flag arithmetic on `EffectType`) — pure flag manipulation, no engine dependency, ideal for `[Flags]`-style bitwise assertions.

## Conflicts observed

- **Master volume and per-track/per-type/per-id volume are computed and clamped through genuinely different call paths** (`SetMasterVolume` writes straight to a mixer dB parameter; everything else composes linearly through Faders and converts once). This isn't a bug, but the docs/XML comments don't call out that master volume is architecturally a mixer-graph multiply rather than a peer term in the same linear product — worth flagging so a future "unify volume computation" refactor doesn't assume it can just add master volume into the `_clipVolume * _trackVolume * _audioTypeVolume` product without changing behavior (it currently is NOT part of that product).

## Could not determine statically

- Exact numeric value/behavior of `AudioSource.outputAudioMixerGroup` switching mid-playback (the engine rule doc flags this as "Unverified / conflicting" already) as it interacts with BroAudio's `SilenceTrackBeforeReturn`/`ReleaseVirtualTrack`/`SetTrackEffect` group swaps — whether the live voice's audible volume glitches for exactly one buffer during these swaps needs to be confirmed in the live Editor with an actual mixer graph, not just by reading source.
- The literal string returned by `BroName.EffectParaNameSuffix` (used to build the per-track send parameter name) — not read directly; needed if a test wants to assert on the exact mixer-exposed-parameter name rather than just its presence/value.
- Actual configured track counts (`Preferences` window settings for Generic/Dominator track pool sizes) in this project's mixer asset — needed to know how many concurrent sounds must be played to deterministically force the pool-exhaustion edge case without an unreasonably large test.
- Whether `SoundManager.Instance.Setting.AudioFilterSlope` (`FilterSlope.FourPole` vs. two-pole) is configured in this project's `RuntimeSetting` asset — affects whether the LowPass/HighPass secondary parameter (`paraName + "2"`) is actually exercised, relevant to the mixer-routing tests above.
- Whether any authored `AudioMixer` asset in this project actually exposes `MainTrackName`/`MainDominatedTrackName`/`MasterTrackName` parameters with the exact names `BroName` expects — a live-Editor check (`SoundManager.Instance.AudioMixer.GetFloat(...)`) is needed to confirm before writing dominator/master-volume tests, since a misconfigured mixer asset would make `SafeGetFloat`/`SafeSetFloat` silently return `false`/no-op rather than fail loudly.
